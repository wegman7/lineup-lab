## 1. Repo layout

**Decision:** one repo (monorepo) with the backend, frontend, evals, and docs together.

```
lineup-lab/
├── README.md                  # pitch, demo link, results, what failed
├── Dockerfile                 # one image: builds the frontend, serves it from the API (§7)
├── docker-compose.yml         # added in stage 2, when Qdrant arrives
├── docs/
│   ├── project-context.md     # original brief
│   ├── functional-spec.md     # what it does
│   ├── technical-spec.md      # this file
│   └── plans/                 # implementation plans, one per milestone
├── backend/                   # Python project
│   ├── pyproject.toml
│   ├── src/lineup_lab/
│   │   ├── api/               # FastAPI app, POST /chat event stream
│   │   ├── agent/             # LangGraph graph, state, router, nodes
│   │   ├── stats/             # DuckDB access, run_sql, schema prompt
│   │   ├── search/            # search_transcripts(), the only code that talks to Qdrant
│   │   ├── players/           # name matching ("CMC" → Christian McCaffrey)
│   │   ├── llm/               # model calls, token and cost tracking
│   │   ├── ingest/            # the refresh job (§3)
│   │   └── config.py          # all environment variables, read in one place
│   ├── evals/                 # test question sets, eval runner, committed results
│   └── tests/
├── frontend/                  # React + TypeScript + Vite
│   ├── package.json
│   └── src/
└── data/                      # gitignored: audio, transcripts, stats.duckdb
```

**Why one repo:**
- An interviewer gets one link.
- Docs live beside the code they describe.
- One CI setup.
- The API's event format (functional spec §6) and the frontend that reads it change together in the same commit.

**Rejected:** separate frontend and backend repos. They add coordination overhead with no benefit for a one-person project.

**Module boundaries that matter:**
- `search/` is the only module that talks to Qdrant. Same rule as `project-context.md`.
- `stats/` is the only module that talks to DuckDB.
- Nodes in `agent/` call those modules. They never call the database clients directly.

This keeps the storage swappable (e.g., moving to Qdrant Cloud or MotherDuck) and keeps every query in one place where it's easy to test.

**Evals live in `backend/evals/`.** They import the backend package directly, so they test the real code path. Results are committed as files, and the Eval results page (functional spec §5.3) is built from them.

## 2. Docs and data storage

- All docs live in `docs/`. Implementation plans go in `docs/plans/`, one per milestone.
- **Transcripts are not committed to git.** They're full transcripts of copyrighted shows, and the public demo only ever shows short snippets.
  - They live in `data/transcripts/` locally.
  - **(to decide in stage 2)** Back them up to a private Cloud Storage bucket. They're the source of truth for rebuilding Qdrant (functional spec §8a), so losing them means re-transcribing everything.
- Audio files and `stats.duckdb` are also gitignored. Both can be regenerated by the refresh job.

## 3. Batch ingestion: a job inside the backend package, not a separate service

**Decision:** the refresh job (functional spec §8a) is part of the `lineup_lab` package, in `ingest/`, with its own entry point: `python -m lineup_lab.ingest`.

- **Why share the package with the API:** ingestion and query must agree exactly on:
  - chunk format and metadata fields
  - the embedding model
  - player name matching
  - Qdrant collection settings

  Shared code makes it impossible for them to drift apart. Separate codebases would eventually disagree without anyone noticing, and retrieval quality would quietly drop.
- **Why separate dependencies:** ingestion needs heavy packages the API never uses (faster-whisper, ffmpeg, feedparser). They go in an optional `ingest` dependency group, so the API image stays small and starts faster on Cloud Run.
- **v1 runs natively on the owner's Mac, not in Docker.** Docker on macOS runs inside a Linux VM with capped memory, which makes long transcription runs slower and harder to watch.
- **Later, if scheduled:** the same code goes into a second image and runs as a **Cloud Run Job**, Cloud Run's product for batch work that runs to completion and exits.

**Rejected:**
- A separate ingestion service. Nothing needs to run continuously.
- An always-on worker with a job queue (e.g., Celery). Real infrastructure to run and explain, for a weekly job.

## 4. Deployment direction: Google Cloud Run

**Decision (direction only, details at deploy time):** the backend and frontend each run as a Docker container on **Google Cloud Run**.

**Why it fits:**
- It runs ordinary containers.
- It scales to zero, so it's close to free when no one is visiting.
- It supports streaming responses, which the SSE stream needs.
- It has a matching product for batch work (Cloud Run Jobs, §3).

**Known issues to resolve when we deploy.** Cloud Run containers are stateless: their disk is wiped when an instance stops, and several instances can run at once.

1. **Qdrant.** The `project-context.md` plan ("Qdrant container next to the app via Docker Compose") doesn't carry over, because Cloud Run doesn't run Docker Compose or keep database files. Candidates:
   - Run Qdrant as a sidecar container with the vector data packaged into the image. The data only changes on refresh, which already triggers a redeploy.
   - A small VM running Qdrant.
   - Qdrant Cloud.
2. **Shared state.** Question logging (functional spec §7a), the daily spending cap (§7), and per-visitor rate limits (§7) need storage outside the container that every instance can see. Candidates: Firestore, a Cloud Storage bucket, or capping the service at one instance.
3. **Frontend → backend routing.** Two separate Cloud Run URLs mean configuring cross-origin access (CORS), or putting both behind one domain.

`stats.duckdb` is not an issue: it's a read-only file that ships inside the API image, as already planned.

## 7. Proof-of-concept decisions

Made for the first milestone (plan: `plans/2026-11-18-poc-stats-agent.md`). Each one is **what / why / rejected**.

**LLM: Claude Opus 5.5 (`claude-opus-5-5`) for every call.** *(owner decision)*
- Why: strongest text-to-SQL, and SQL accuracy is the headline number. The model is one setting (`LLM_MODEL`), and depth is tuned per step with `effort` (router `low`, SQL `medium`, answer `low`).
- Rejected for now: a cheap router model plus a strong answer model. It's a good experiment, but only once there's a baseline to compare against.

**Python tooling: uv + ruff + pytest.**
- Why: uv manages the Python version, the virtualenv, and a lockfile in one fast tool. ruff replaces black, isort, and flake8. pytest is the default.
- Rejected: Poetry (slower, no Python version management), pip + requirements.txt (no lockfile for transitive dependencies).

**Graph skeleton: `route → resolve → gen_sql ⇄ run_sql → answer`, with `decline` for everything else.**
- The SQL retry is a **graph edge** (`run_sql → gen_sql` on error, at most 3 attempts), not a tool loop inside the model.
- Why: each attempt is a visible, countable step. The cap is enforced in our code. Every attempt shows up in the trace and in the eval's "attempts used" number.
- Rejected: giving the model a `run_sql` tool and letting it loop. The retries would live inside the model's loop, which makes them harder to cap and measure. Revisit if questions start needing several queries.

**Stats tables: four curated tables plus `meta`, with the schema prompt generated from DuckDB.**
- `players`, `weekly_stats` (~40 fantasy-relevant columns out of nflverse's 150), `snap_counts`, `games`.
- Column meanings live in DuckDB `COMMENT ON COLUMN`. The schema prompt is built from `information_schema`, so it can't drift from the data.
- Rejected: the raw 150-column table (wastes tokens, adds confusable columns), and a hand-written schema description (drifts).

**Player names: a deterministic resolver, not the LLM.**
- Order: alias file → exact name → first or last name → fuzzy match (`difflib`). Ties go to the player with more PPR points in the loaded data, and the agent "assumes" (and says so) when the top candidate has at least 3× the next one's points.
- Why: testable, explainable, free, and shown in the trace.
- Rejected: asking the LLM (not testable, costs a call), embedding similarity (overkill for about 2,000 names).

**SSE payloads.**
- `step {id, kind, status, summary, detail, duration_ms}`, `token {text}`, `source {n, kind, label, columns, rows, row_count, truncated}`, `done {ttft_ms, total_ms, cost_usd, input_tokens, output_tokens}`, `error {message}`.
- The `chat_id` comes back as the `X-Chat-Id` response header.
- Defined once in `agent/events.py`. `frontend/src/api/types.ts` mirrors it.

**SQL evals: YAML cases with a reference SQL, graded by execution match.**
- The agent's result passes when the row counts match and every column of the reference result appears among its columns (order-insensitive, rounded).
- Why: reference SQL stays correct after a data refresh, where hard-coded numbers go stale.
- Known limitation: row alignment across columns isn't checked.

**PoC shared state (§4.2): one Cloud Run instance.** *(owner decision)*
- `max-instances=1`, so the per-IP limit and daily spending cap can live in memory and still be correct.
- The real store is decided before stage 3, when question logging arrives.

**Frontend routing (§4.3): one container.**
- FastAPI serves the built React app from the same origin. No CORS, one service, one deploy.
- Rejected: two Cloud Run services plus CORS configuration.
